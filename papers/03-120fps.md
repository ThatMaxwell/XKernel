# One Hundred and Twenty

*Paper 3 of 5: how a virtual machine gets near 120 frames per second*

---

## The claim

XKernel's boldest promise is that an operating system running inside it can feel native: smooth scrolling, smooth windows, and games close to 120 frames per second.

This paper explains why that's possible, what has to be true for it to work, and where its honest limits are. Nothing here is invented from scratch. Every technique already exists and is used by people today, usually in fiddly, hand-tuned setups. XKernel's job is to make them the default.

---

## 1. Where a VM's frames actually go

Follow one frame through a typical desktop VM (say, VirtualBox or a default QEMU setup):

1. The guest app asks the guest's graphics driver to draw.
2. The guest's "graphics card" is **emulated**: a fake device implemented in software on the host.
3. The host either draws the frame on the CPU, or translates the guest's commands into host graphics calls.
4. The finished frame is **copied** into a window owned by the host's VM app.
5. The host's desktop compositor composites that window together with everything else.
6. The frame finally reaches the screen.

Every step adds latency and burns CPU. The emulated GPU in step 2 is the main villain: software can't pretend to be a modern GPU at modern speeds.

**So the 120 fps plan is mostly about step 2: give the guest a real GPU.**

---

## 2. The CPU part is already fast

The CPU side of virtualization is effectively solved:

- **Hardware virtualization** (VT-x/AMD-V, arm64 virtualization extensions) runs guest instructions directly on the CPU.
- **Hardware-assisted paging** (Intel EPT, AMD NPT) translates guest memory without slow software tricks.
- **virtio** devices (disk, network, input) are paravirtualized: the guest knows it's virtual and cooperates, avoiding expensive emulation.

XKernel adds tuning on top:

- **CPU pinning:** each Kernel's vCPUs are pinned to specific physical cores, so they don't bounce around and lose their cache.
- **Host isolation:** the host's few processes live on their own core(s), away from guests.
- **Huge pages:** guest RAM backed by large pages, so memory translation costs less.
- **NUMA awareness** on big machines: a Kernel's memory stays near its cores.

Together, these get a guest's CPU performance very close to bare metal. This is well-documented territory.

## 3. Giving a guest a real GPU

There are three ways, each with a different trade-off.

### 3a. VFIO GPU passthrough: one GPU, one Kernel

The whole physical GPU is detached from the host and given to one Kernel. The guest installs the normal vendor driver (NVIDIA, AMD, Intel) and talks to the hardware directly, isolated by the IOMMU.

- **Performance:** close to native. This is how people game on Windows VMs today.
- **Cost:** that GPU now belongs to that Kernel only. The host and other Kernels can't use it at the same time.
- **Requirements:** an IOMMU (VT-d/AMD-Vi), a motherboard with sane IOMMU groups, and in practice a second GPU, often the integrated one, for the host and other Kernels.

**This is XKernel's first fast path.** One "gaming" Kernel gets the big GPU. Everything else shares the integrated one.

### 3b. SR-IOV: one GPU, many Kernels

**SR-IOV** (Single Root I/O Virtualization) lets one physical device present itself as several "virtual functions", each assignable to a different guest with hardware-enforced separation.

- **Performance:** each slice runs on real GPU hardware, with no emulation.
- **Big advantage:** several Kernels get real GPU acceleration at the same time. It's the dream for a tiling multi-VM machine.
- **Reality:** support depends on the GPU and driver. Recent Intel graphics generations support SR-IOV on Linux. On NVIDIA and AMD, the equivalent is mostly limited to data-center and pro cards with licensed software. XKernel should treat SR-IOV as the best path where available and detect it automatically.

### 3c. virtio-gpu with Venus or virgl: shared, translated

The guest uses a paravirtual GPU. Its OpenGL (virgl) or Vulkan (Venus) commands are serialized and executed on the host's GPU.

- **Performance:** good for desktops and light 3D, below native for heavy games. Every command crosses the guest-host boundary.
- **Advantage:** works on almost any hardware, with no passthrough and no special GPU.
- **Fit:** the default for "light" Kernels like terminals, desktops and development environments.

### Summary

| Path | Speed | Kernels per GPU | Hardware needs |
|---|---|---|---|
| VFIO passthrough | ~native | 1 | IOMMU, ideally 2 GPUs |
| SR-IOV | ~native | many | SR-IOV-capable GPU + driver |
| virtio-gpu (Venus/virgl) | good, not native | many | almost any |

## 4. Getting the frames into a tile: Looking Glass

When a Kernel renders on a passed-through GPU, its frames are in *that GPU's* memory, and the GPU is plugged into... nothing. Traditionally you'd attach a physical monitor to the guest's GPU. That works, but then the guest isn't in a tile.

**Looking Glass** solves this. Inside the guest, a small program captures each finished frame and writes it into a **shared memory region** (an IVSHMEM / KVMFR device) that the host can read directly. On the host, the frame is uploaded as a texture and drawn. No video encoding, no network protocol, no extra compression.

- **Latency:** very low. Looking Glass is used by people gaming in VMs who are sensitive to latency.
- **XKernel's role:** `xcomp` integrates Looking Glass's host side directly, so a GPU-backed Kernel's frames land straight in its tile.
- **Practical detail:** passthrough GPUs often need a display attached (or a dummy plug or virtual display driver) to render at all. XKernel's setup tooling should handle this.

## 5. Making the host disappear

The second half of the bet: **a weightless host.**

On a normal host, VM frames compete with everything else: the desktop shell, its widgets, search indexing, sync clients, telemetry, an AI assistant. XKernel's host has none of these. Its whole visible job is:

1. Draw a blurred wallpaper. It's computed once and cached, so it costs nothing per frame.
2. Draw tile borders and a focus animation.
3. Composite Kernel frames into tiles.

`xcomp` should composite **directly onto the display** (no nested compositor) and support **direct scanout**: when a Kernel is fullscreen, its frame can be sent to the display without being composited at all. Fullscreen at 120 Hz should cost the host almost nothing.

---

## 6. The full pipeline, XKernel style

For a GPU-backed Kernel in a tile:

1. A guest app draws on a **real GPU** (VFIO or SR-IOV).
2. Looking Glass in the guest writes the frame into **shared memory**.
3. `xcomp` imports it as a texture, with no copy over the network and no encoding.
4. `xcomp` composites it into the tile over a cached blurred wallpaper, or scans it out directly when fullscreen.
5. The frame reaches the screen.

Compare that to the six-step path in section 1: no emulated GPU, no fat host desktop, no wasted copies.

---

## 7. Honest limits

XKernel promises "can be smooth", not "is always smooth". The limits:

- **No real GPU, no 120 fps.** On hardware without passthrough or SR-IOV, light Kernels are smooth for desktop work but heavy 3D won't hit native speeds.
- **One big GPU means one gaming Kernel.** Without SR-IOV, only the Kernel holding the passed-through GPU gets full speed.
- **Anti-cheat.** Some online games detect virtual machines and refuse to run. That's a policy choice by game makers, not something XKernel can or should get around.
- **Save and resume plus passthrough** is hard (see Paper 2, section 5).
- **Laptops are tricky.** Many laptops wire the display through the integrated GPU and give the discrete GPU no outputs. Passthrough still works, but the setup is more complicated.
- **"120"** depends on the guest's workload, the GPU and the display. It's a target and a design goal, not a guaranteed number.

---

## 8. What we'll measure

When XKernel runs, we publish numbers, not adjectives:

- Frame time (average and 1% lows) of the same game on bare metal versus an XKernel Kernel
- Input-to-photon latency in a tile versus fullscreen
- Host CPU and GPU usage with 1, 2 and 4 Kernels visible
- Save and resume times per GB of guest RAM

If XKernel is fast, the numbers will show it. If it isn't, the numbers will tell us where to work.
